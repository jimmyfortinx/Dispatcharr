Fixing repeated HTTP 456 failures on Stalker portal streams

A scoped fix for the retry loop hammering Stalker portals with fresh sessions instead of backing off, using the channel 185.80.197.39 outage as the reproducing case.

Plan Stalker portal live_proxy

#Problem

Live channels backed by a Stalker/Ministra portal (observed on host 185.80.197.39) fail to start playback even though the portal accepts every request up to the final step. Container dispatcharr on superdocker (10.1.2.11) shows this pattern in logs, five times in ~10-16 seconds, before giving up and switching to the next stream: 

handshake        -> 200
get_events       -> 200
create_link      -> 200 (new play_token)
GET /play/live.php -> HTTP 456   <-- portal rejects playback

HTTP 456 on Stalker/Ministra portals is a portal-side rejection, almost always meaning the MAC/account is already considered to have an active connection (concurrent-connection limit). Dispatcharr's current retry behavior makes this worse rather than better.

#Root cause (confirmed by reading the code, not guessed)

  • Every retry re-authenticates from scratch. apps/proxy/live_proxy/url_utils.py:51 (_resolve_live_stream_context) constructs a brand-new StalkerClient on every call. Since StalkerClient.__init__ sets _prepared_portal_url = None, the session-reuse guard in apps/m3u/stalker.py:883-892 (prepare_authenticated_session) never actually fires across retries — each retry redoes handshake + authenticate + watchdog even though a session was just established seconds earlier.
  • The retry loop calls this on every attempt. apps/proxy/live_proxy/input/manager.py:646-796 (StreamManager.run) calls self._refresh_runtime_stream_url(reason="retry") on every retry (line 654-657), which flows straight into the fresh-client path above. Backoff between attempts is only min(.25 * failures, 3) seconds (lines 759, 790) — not nearly long enough for a portal-side connection-limit rejection to clear, and it's the same backoff regardless of failure type.
  • The HTTP status code never reaches the retry loop. HTTPStreamReader.start() (input/http_streamer.py:30-47) returns immediately after launching the reader thread, before the GET even fires. _read_stream (lines 49-77) checks if self.response.status_code != 200: logger.error(...); return — it only logs and exits; the code is never stored or surfaced. So _establish_http_connection (manager.py:1491-1546) has no way today to tell a 456 apart from any other transport failure.
  • No portal-side session teardown exists, anywhere in apps/m3u/stalker.py — confirmed by search. This is expected: standard Stalker/Ministra portals don't expose a logout action; sessions expire server-side via watchdog timeout. Not something to invent here.

#Constraints

  • No invented portal endpoints — only use handshake / do_auth / get_events / create_link, which already exist.
  • Don't touch XC or plain M3U code paths — Stalker-only.
  • Don't change max_retries defaults or rearchitect the retry loop.
  • Session caching must default to today's behavior for every other caller (channel preview, discovery flows) — only the manager's retry path opts in.

#Fix (3 parts)

  1. Surface the rejection status code up to the retry loop.
    • apps/proxy/live_proxy/input/http_streamer.py — add self.last_status_code = None in __init__; set it in _read_stream right before the existing if self.response.status_code != 200: early return.
    • apps/proxy/live_proxy/input/manager.py (_establish_http_connection, ~1491-1546) — after the reader thread ends, read self.http_reader.last_status_code. If it's a known portal-rejection code (456 first; leave room to extend), call the existing self._record_transport_failure(reason="stalker_portal_rejected", details={"status_code": code}) helper (already used elsewhere, e.g. for reconnect logging at line 681-692) instead of leaving the failure unclassified.
  2. Back off longer, specifically for this failure class.
    • At the two backoff sites (manager.py:759 and :790), read reason = (self.last_transport_failure or {}).get("reason"). When reason == "stalker_portal_rejected", use a materially longer schedule (e.g. min(2 * failures, 10) seconds) instead of the default min(.25 * failures, 3).
    • Log a clear, specific line: "Portal rejected connection (HTTP 456) for <mac> — likely concurrent-connection limit on this Stalker account; backing off Ns before retry", so this is diagnosable straight from logs next time, instead of re-deriving it from a packet trace.
  3. Reuse the Stalker session across retries within one channel's connection lifecycle.
    • StreamManager instances already persist per channel_id for the whole retry lifetime (registered in apps/proxy/live_proxy/server.py:806-818). Add self._stalker_client_cache = {} in StreamManager.__init__.
    • Thread an optional stalker_client_cache parameter through get_stream_info_for_switch → _build_runtime_stream_info → _resolve_live_stream_context in apps/proxy/live_proxy/url_utils.py, default None everywhere it isn't already threaded (so channel preview / discovery / other callers behave exactly as today).
    • In _resolve_live_stream_context, when a cache dict is passed: key by (m3u_account.id, mac), reuse the existing StalkerClient if present instead of constructing a new one. This is the one change that actually makes prepare_authenticated_session's existing reuse guard (stalker.py:883-892) do anything — no changes needed inside stalker.py itself.
    • manager.py's call to get_stream_info_for_switch inside _refresh_runtime_stream_url (~1865-1910) passes self._stalker_client_cache.

#Risks and tradeoffs

Thread-safety under gevent
The cached StalkerClient (and its requests.Session) is only ever touched from the single greenlet running that channel's StreamManager.run() retry loop — never concurrently. No locking needed, but this is an assumption worth stating explicitly rather than discovering later.
Stale session (portal-side expiry)
If the cached session's watchdog lapses between retries, the next create_link/auth call fails with an auth-shaped error. resolve_playback_url already retries once with _prepared_portal_url reset on exactly this class of error (stalker.py:1074-1087) — stale sessions self-heal at the cost of one extra round trip. No new code needed for this case.
Cache scope / eviction
Scoped to one StreamManager instance (one per channel_id), not a global/process-wide cache. Simple, and avoids stale entries surviving a channel teardown or a mid-flight portal/MAC config edit. Tradeoff: two different channels sharing the same Stalker MAC still get two independent sessions/clients and can still contend for the same concurrent-connection slot on the portal — this fix doesn't solve that cross-channel case, see Open Questions.
Backwards compatibility
Every new parameter defaults to None/off. Preview, discovery, and any other existing caller of url_utils.py functions keeps today's exact behavior.
Open question: if two channels in Dispatcharr are configured to use the same Stalker MAC/account concurrently, this fix does not prevent them from independently opening two sessions and contending for the portal's connection limit — each StreamManager caches its own client. A global per-MAC cache would fix that but needs cross-greenlet locking and invalidation-on-config-change, which is a materially bigger change than this fix. Worth confirming with the portal/account setup for 185.80.197.39 whether this is actually happening (e.g. multiple channels mapped to the same M3U/Stalker account) before deciding whether it's in scope.

#Test / verification plan

  • Unit test: HTTPStreamReader sets last_status_code on a mocked non-200 response.
  • Unit test: the backoff branch — inject a fake last_transport_failure with reason stalker_portal_rejected and assert the longer schedule is used instead of the default.
  • Unit test: _resolve_live_stream_context with a cache dict reuses the same StalkerClient instance across two calls for the same (account, mac) — assert handshake/authenticate are only invoked once across both calls (mocked).
  • Manual verification: deploy to superdocker, re-tail docker logs dispatcharr | grep 185.80.197.39, confirm retries space out more, redundant handshake/get_events/create_link triples per failed attempt drop, and the new "portal rejected (456)" log line appears.

#Out of scope

  • Rewriting the retry/backoff architecture generally.
  • Changing default max_retries or per-profile max_streams semantics.
  • XC/plain-M3U provider code paths.
  • A global cross-channel per-MAC session cache (see open question above).
  • Inventing a portal logout/disconnect call that the Stalker protocol doesn't provide.
